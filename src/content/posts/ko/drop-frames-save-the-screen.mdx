카메라는 초당 60장을 보낸다. 추론은 그 속도를 못 따라간다. 그래서 엔진은 프레임을 버린다.

온디바이스 비전 카메라 앱을 만들다 보면 가장 먼저 부딪히는 벽이 있다. 카메라는 초당 수십 장의 프레임을 쉬지 않고 밀어내는데, 그 프레임을 "이해" 하는 ML 추론은 한 장에 수십 밀리초가 넘게 걸린다. 둘을 순진하게 이어 붙이면, 카메라가 아닌 추론 속도에 발목이 잡혀 화면이 뚝뚝 끊긴다. 카메라가 60fps여도 추론이 10fps면, 보이는 건 10fps짜리 슬라이드쇼다.

처음 떠오르는 해법은 큐다. 들어오는 프레임을 버퍼에 쌓고, 추론이 하나씩 꺼내 처리하면 되지 않나. 문제는 지연이다. 추론이 프레임 생산 속도보다 느린 순간, 큐는 영원히 줄지 않는다. 계속 쌓이기만 한다. 그러면 화면에 그려지는 인식 결과는 점점 과거의 것이 된다. 1초 전에 카메라 앞을 지나간 글자의 박스가 지금 화면에 떠 있는 것이다. 실시간 카메라에서 이건 버그보다 나쁘다 — 틀린 게 아니라 뒤늦은 결과니까. 게다가 메모리도 같이 새어 나간다. 4K 프레임 한 장이 수 MB인데, 그걸 큐에 무한정 쌓으면 끝이 뻔하다.

실시간에서 오래된 프레임은 쓸모가 없다. 1초 전 장면을 정확히 분석해봐야 사용자가 보는 지금과는 무관하니까. 그래서 정책은 단순해진다. *추론이 바쁘면 그동안 들어온 프레임은 버린다. 단, 가장 최근 한 장만 빼고.*

이 "쌓지 않고 최신 한 장만 남기는" 로직을 `InferenceEngine` 이라는 actor 안에 가뒀다. actor를 쓴 이유는 명확하다. 프레임은 카메라 콜백(백그라운드 큐)에서 들어오고, 추론도 비동기로 돈다. 상태(`pending`, `isProcessing`)를 여러 곳에서 건드리는데, 그 동기화를 락으로 직접 하는 대신 actor에게 맡긴 것이다.

```swift
func submit(_ frame: Frame) {
    pending = frame
    guard !isProcessing else { return }   // 바쁘면 → 최신만 남기고 나머지는 드롭
    isProcessing = true
    drainTask = Task { await self.drain() }
}

private func drain() async {
    defer { isProcessing = false }
    while let frame = pending {
        pending = nil
        let objects = await infer(frame, requests)   // 일시중단: 이 사이 들어온 프레임은 pending을 덮어쓴다
        continuation.yield(PipelineResult(objects: objects, ...))
    }
}
```

핵심은 `pending` 이 큐가 아니라 *한 칸짜리 슬롯* 이라는 점이다. `submit` 은 들어온 프레임으로 그 한 칸을 무조건 덮어쓴다. 추론이 진행 중(`isProcessing == true`)이면 거기서 끝 — 새 `drain` 을 띄우지 않고 그냥 돌아간다. 추론은 `await infer(...)` 에서 일시중단되는데, 바로 그 사이 도착한 프레임 다섯 장은 전부 `pending` 한 칸을 차례로 덮어쓰고 마지막 한 장만 살아남는다. 추론이 끝나면 `drain` 의 `while` 이 그 마지막 프레임을 집어 다음 회차를 돈다.

`submit` 이 `Task { drain() }` 을 fire-and-forget으로 띄우는 것도 의도적이다. 프레임을 공급하는 쪽(`run` 의 for-await 루프)이 추론을 기다리지 않게 하려는 거다. 공급과 처리가 같은 흐름에 묶이면 결국 다시 처리 속도에 공급이 끌려간다.

여기서 작은 결정 하나가 큰 차이를 만든다. `InferenceEngine` 은 Vision을 직접 호출하지 않는다. 대신 추론을 주입받는다.

```swift
public typealias InferenceFunction = @Sendable (Frame, [InferenceRequest]) async -> [RecognizedObject]
```

엔진이 아는 건 "프레임을 주면 인식 결과가 비동기로 돌아온다" 는 계약뿐이다. 그 안이 진짜 `VNRecognizeTextRequest` 인지 테스트용인지는 모른다. 덕분에 엔진의 드롭 정책과 실제 추론이 깔끔히 분리된다. 프로덕션에선 Vision 구현을 주입하고, 테스트에선 내 마음대로 멈췄다 풀 수 있는 목데이터를 주입하면 된다.

이게 왜 중요하냐면 — 시뮬레이터에서는 카메라를 사용할 수 없다. 만약 드롭 로직이 카메라에 묶여 있었다면, 이 핵심 로직을 검증하려면 매번 실기기가 필요했을 것이다. 추론을 주입형으로 빼니, 엔진의 가장 중요한 부분을 기기 없이 CI에서 검증할 수 있게 됐다.

"바쁠 때 프레임을 버린다" 는 걸 테스트로 어떻게 구현할까? 가장 쉬운 유혹은 "빠르게 열 장 쏟아붓고 처리된 게 열 장보다 적은지 보는" 방법이다. 하지만 그건 스케줄러 운에 기대는 flaky 테스트다. 우연히 문제없이 처리될 수도 있고 아닐 수도 있다.

그래서 타이밍 운에 기대지 않고, 그 상황을 직접 만들어내기로 했다. 게이트 두 개를 둔다. 하나는 추론이 "나 시작했어" 라고 알리는 신호, 다른 하나는 테스트가 "이제 끝내도 돼" 라고 푸는 허가. 이걸로 "추론이 도는 도중에 프레임이 도착하는" 상황을 손으로 만들어낸다.

```swift
await engine.submit(frame(0))   // 추론(0) 시작
await started.wait()            // 결정론적으로: 추론(0)이 지금 돌고 있다 (바쁨)
await engine.submit(frame(1))   // 바쁨 → 드롭
await engine.submit(frame(2))   // 바쁨 → 드롭, pending = frame(2)
await proceed.release()         // 추론(0) 끝 → drain이 pending(2)를 집음 → 추론(2) 시작
await started.wait()            // 추론(2)가 돈다 (즉 드롭된 게 아니라 선택됐다)
await proceed.release()
#expect(processed == [0, 2])    // frame 1은 드롭. 첫 장 + 마지막 장만, 순서대로.
```

`sleep` 도 없고 프레임을 한꺼번에 쏟아붓지도 않는다. 게이트가 타이밍을 못 박아서 이 테스트는 50번을 돌려도 같은 답을 낸다. 결과는 `[0, 2]` — 바쁜 사이 들어온 frame 1은 사라지고, 첫 프레임과 가장 최근 프레임만 처리됐다는 증거다. 이 한 줄이 드롭 백프레셔의 계약 전부다.

정리하면 이 설계의 뼈대는 *분리* 다. 화면은 카메라의 시계(60fps)로 흐르고, 추론은 자기가 감당할 수 있는 느린 시계로 흐른다. 그 사이의 빈칸은 "마지막 결과 유지" 로 메운다 — 새 인식이 올 때까지, 직전 박스를 그대로 들고 있는 것이다.

큐를 버리고 슬롯 하나만 남긴 건 결국 *"오래된 정답보다 약간 늦은 최신이 낫다"* 는 판단이다. 실시간이라는 건 모든 프레임을 처리하겠다는 약속이 아니라, 지금에 최대한 붙어 있겠다는 약속이다. 프레임을 아끼려다 화면을 잃느니, 프레임을 버려서 화면을 살리는 편이 낫다.
