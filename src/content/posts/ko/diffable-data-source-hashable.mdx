`UICollectionViewDiffableDataSource` 를 처음 쓰면 컴파일러가 대뜸 요구하는 게 있다. item 타입이 `Hashable` 이어야 한다는 것. `Equatable` 도 아니고 굳이 `Hashable` 이다. 단순 문법 제약처럼 보이지만, 이 요구 하나에 diff 알고리즘의 동작 원리와 "무엇을 같은 행으로 볼 것인가" 라는 설계 결정이 통째로 들어 있다.

먼저 둘의 차이. `Equatable` 은 "두 값이 같은지(`==`) 비교할 수 있다" 는 계약이다. 배열에서 `contains` 를 호출하면 첫 칸부터 끝까지 `==` 로 훑는다 — 100만 개 중 마지막에 있으면 100만 번 비교, O(n)이다. `Hashable` 은 "값을 정수 하나(hash)로 압축할 수 있다" 는 계약이고, `Set`·`Dictionary` 는 그 hash로 사물함 번호를 계산해 단번에 넣고 꺼낸다 — 100만 개든 1억 개든 O(1)이다. `Hashable` 은 `Equatable` 을 상속하므로, hash가 같은 후보들 안에서 최종 동일성은 `==` 로 가린다.

Diffable Data Source가 하는 일은 결국 두 스냅샷(이전 상태 vs 새 상태)의 차이를 계산하는 것이다. 무엇이 추가됐고(insert), 삭제됐고(delete), 이동했는지(move)를 뽑아내야 그 셀만 정확히 건드린다. 이걸 `Equatable` 배열만으로 하면 옛 배열의 각 아이템이 새 배열 어디로 갔는지 찾느라 이중 루프를 돈다. O(N²)이다. 수백 개만 돼도 메인 스레드가 멈칫하고 프레임이 떨어진다.

이 문제를 O(N)으로 떨어뜨리는 클래식이 Paul Heckel이 1978년에 낸 해시 기반 선형 diff다. hash 없이는 이 계열의 알고리즘이 성립하지 않는다. Diffable Data Source가 item에 `Equatable` 이 아니라 `Hashable` 을 요구하는 건 정확히 이 지점과 맞닿아 있다.

Heckel의 골자는 이렇다. 옛 배열과 새 배열을 각각 한 번씩만 훑어 hash 테이블에 "이 아이템이 양쪽에서 각각 몇 번, 어느 인덱스에 나왔나" 를 기록한다. 그다음 "옛쪽에서도 딱 한 번, 새쪽에서도 딱 한 번" 나온 고유 아이템 — 앵커(anchor) — 를 찾아 둘을 잇는다. 양쪽에 하나씩뿐이니 값이 바뀐 게 아니라 위치만 옮겼거나 그대로인 게 확실하다. 앵커를 찾았으면 그 앞뒤 칸을 hash 테이블로 직접 매핑해(`i+1` ↔ `j+1`) 같으면 또 잇는다 — 반대편 전체를 뒤질 필요 없이 특정 인덱스만 O(1)로 본다. 끝까지 선이 안 그어진 아이템은 insert나 delete, 선은 있지만 순서가 뒤틀린 건 move로 판정한다. 이중 루프 없이 일렬 스캔 대여섯 번으로 끝난다. 매 단계를 O(1)로 받쳐주는 게 hash다.

여기서 Diffable을 쓰는 사람이 진짜 알아야 할 게 나온다. *item의 `Hashable` 이 곧 그 행의 정체성(identity) 정의다.* diff는 hash와 `==` 로 "이게 같은 아이템인가" 를 판단하는데, 그 기준을 짜는 건 당신이다.

흔한 함정이 여기 있다. struct에 `Hashable` 을 synthesize 시키면 *모든 저장 프로퍼티* 가 hash와 `==` 에 들어간다.

```swift
struct Person: Hashable {
    let id: UUID
    var name: String
    var age: Int        // age만 바뀌어도 hash가 달라진다
}
```

이러면 이름 "Aiden", 나이 25인 행에서 나이만 26으로 바뀌어도 — diff 입장에선 hash가 달라졌으니 *완전히 다른 아이템* 이다. 결과는 update가 아니라 delete + insert. 셀이 부드럽게 갱신되는 게 아니라 통째로 갈리고, 선택 상태나 진행 중이던 애니메이션도 날아간다.

그래서 정석은 정체성과 값을 분리하는 거다. item identifier에는 안 변하는 고유 id만 넣어 hash/`==` 의 기준으로 삼고(정체성), 화면에 보일 값이 바뀌면 그건 `reconfigureItems` / `reloadItems` 로 따로 알린다(값 갱신). 그러면 diff는 "같은 행인데 내용만 바뀜" 을 정확히 잡아 그 셀만 다시 그린다. iOS 15+ 에서는 아예 스냅샷의 item 타입을 가벼운 id로 두고, 셀 구성은 `CellRegistration` + `reconfigureItems` 로 떼어내는 게 권장 패턴이다.

`Hashable` 을 강제하면 그만큼 hash 테이블 메모리를 더 쓴다. 적재율(load factor) 유지를 위해 늘 일정 비율은 빈 채로 두고, 충돌 대비 여유도 잡는다. Apple은 그 메모리를 기꺼이 내줬다. 요즘 아이폰 RAM은 기가바이트 단위라 수만 개 데이터의 hash 테이블 몇 MB는 타격이 없지만, 메인 스레드가 한 프레임을 그리는 약 16ms 안에 diff가 O(N²)로 늘어지면 60fps가 무너지는 건 치명적이니까.

결국 Diffable Data Source의 `Hashable` 요구는 문법적 변덕이 아니다. 메모리를 조금 내주고 CPU 시간을 극적으로 아껴, diff를 O(N)에 끝내고 화면을 부드럽게 유지하겠다는 트레이드오프의 입구다. 그리고 그 trade의 첫 단추는 — item의 `Hashable` 에 무엇을 정체성으로 넣을지를 당신이 정하는 데 있다.
