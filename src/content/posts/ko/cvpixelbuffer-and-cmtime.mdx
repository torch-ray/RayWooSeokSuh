Apple의 미디어 API를 처음 만지는 iOS 엔지니어는 보통 두 번 당황한다. 한 번은 `CVPixelBuffer`가 struct가 아니라 class라는 사실. 또 한 번은 `CMTime`이 Double 같은 친숙한 실수 타입이 아니라 `value/timescale` 형태의 유리수라는 사실. Swift 6의 actor concurrency 위에 얹으려고 하면 `@unchecked Sendable`까지 직접 명시해야 하는 상황을 만난다. 모던 Swift가 보여준 안전성과는 거리가 멀어 보인다.

그런데 이 둘은 시대에 뒤떨어진 API가 아니다. 정반대로, 미디어가 가진 두 물리적 제약 — *copy는 비싸고, drift는 누적된다* — 위에 정확히 맞춰진 설계다.

먼저 `CVPixelBuffer`. 4K 프레임 한 장은 YUV 10-bit 기준으로 약 16MB. 60fps라면 1초에 단일 컨슈머만 봐도 약 1GB의 데이터가 오간다. 실제 파이프라인엔 보통 GPU, NPU, 인코더 세 명의 컨슈머가 동시에 붙는다. GPU는 화면에 그리고, NPU는 모델 추론에 쓰고, 인코더는 파일로 저장한다. 같은 프레임을 struct처럼 값 복사로 돌리면 매초 3GB 이상의 메모리 복사가 발생하고, 디바이스는 즉시 throttling에 걸린다.

그래서 Core Video는 통합 메모리의 특정 주소에 픽셀을 한 번만 쓰고, 8바이트 포인터만 돌려가며 참조하도록 `CVPixelBuffer`를 reference 타입으로 정의했다. 추가로 모자이크, 뷰티 필터, 워터마크 같은 후처리 요구가 있어 완전한 read-only가 아니라 `CVPixelBufferLockFlags` 기반의 read/write 잠금을 갖춘 가변 참조 객체로 만들었다. 메모리 풀(`CVPixelBufferPool`)을 따로 둔 것도 같은 맥락이다. 60fps의 새 프레임마다 alloc/free를 하면 그것 자체가 throttling의 원인이 된다.

Swift 6의 concurrency 모델 위에 이걸 얹는 순간 컴파일러와 마찰이 시작된다. `CVPixelBuffer`는 내부에 raw 포인터를 들고 있는 mutable reference 타입이라 Sendable이 아니다. actor 경계를 넘기려 하면 컴파일러가 거부한다.

```swift
public struct Frame: @unchecked Sendable {
    public let pixelBuffer: CVPixelBuffer
    public let timestamp: CMTime
    public let depth: CVPixelBuffer?
}
```

여기서 흔히 빠지는 함정은 *얕은 불변성(shallow immutability)의 착시* 다. struct 안에서 `let pixelBuffer`로 선언해도 잠기는 건 reference 그 자체뿐이다. `CVPixelBufferLockBaseAddress` 같은 C 함수가 그 reference가 가리키는 메모리로 들어가 픽셀을 뜯어고치는 건 컴파일러가 막을 길이 없다. `@unchecked Sendable`은 "이 버퍼를 read-only로만 다루겠다"는 개발자 측 보증 수표이지, Swift가 검증해주는 안전성이 아니다.

실전 함의는 단순하다. 버퍼는 반드시 `Frame` 같은 wrapper 단위로 actor 사이를 오가야 한다. `frame.pixelBuffer`만 따로 빼서 보내려 하면 컴파일러가 다시 잡는다. wrapper 단위 유통이 곧 actor 안전성의 명시적 경계다.

`CVPixelBuffer`가 메모리 축의 답이라면, `CMTime`은 시간 축의 답이다. 같은 패턴이 *drift* 라는 또 다른 물리적 제약에 대응한 결과다. 짧은 단발 측정엔 `TimeInterval` (= Double) 이 가볍고 충분하다. 그러나 비디오는 마라톤이다. 90분짜리 영상에 30fps라면 162,000장의 프레임이 들어가고, 각 프레임의 PTS(presentation timestamp)가 누적된다. 문제는 `1.0 / 30.0` 같은 값이 이진 부동소수점으로 정확히 표현되지 않는다는 점이다. 매 덧셈마다 미세한 반올림 오차가 생기고, 16만 번을 누적하면 그 오차들이 자라나 어느 순간 비디오 클럭과 오디오 클럭이 미세하게 어긋난다. 입모양 sync가 깨지는 그 순간이다.

`CMTime`은 이걸 유리수로 회피한다. `CMTime(value: 1, timescale: 30)`은 *정확히* 1/30초고, 같은 timescale 안에선 정수 덧셈으로 환원되어 수만 번을 더해도 오차가 0이다. 90분짜리 영상의 마지막 프레임 PTS는 `CMTime(value: 161999, timescale: 30)`으로 그냥 정수 덧셈이고, 그래서 비디오 편집기에서 정확한 프레임으로 seek할 수 있다. Apple이 미디어 전반에 걸쳐 `Double` 대신 `CMTime`을 쓰는 이유는 우아함이 아니라 산수다.

두 결정이 자리잡았을 때 무엇이 가능해지는지는 자동 캡처 같은 기능에서 깔끔히 드러난다. 카메라는 30fps로 프레임을 던지고, Vision은 약 33ms마다 한 장씩 받아 confidence를 뱉는다. confidence가 임계점 — 예를 들어 0.95 — 을 넘고 타깃이 가이드라인 안에 안착한 찰나, 코드가 사용자 대신 셔터를 누른다. 가운데가 뚫린 검은 반투명 마스크는 카메라가 그 영역만 보는 게 아니라, 센서는 늘 방 전체를 찍고 있고 `CAShapeLayer`로 얹은 시각적 유도일 뿐이다. 분석 대상만 `regionOfInterest`로 좁히면 되는데, 정규화 좌표(`0.0 ~ 1.0`)와 좌측 하단이 `(0, 0)`인 Y축 반전 좌표계라는 두 가지만 주의하면 된다. 이 흐름이 매끄럽게 굴러가는 건 매 프레임이 zero-copy로 도착하고 (`CVPixelBuffer`), 시간 도장이 누적 오차 없이 쌓이기 때문 (`CMTime`)이다.

두 API 모두 단일한 패턴 위에 있다. 미디어는 *대량* 이고 *지속적* 이다. 한 번에 한 프레임만 다루는 산수가 아니라 초당 수십 장, 시간 단위로 누적되는 산수다. struct의 값 복사 시맨틱과 Double의 부동소수점은 둘 다 짧은 연산엔 옳고 긴 누적엔 틀린 도구다. Apple의 미디어 API는 그 차이를 안 데서 한 가지를 선택했을 뿐이다.

이걸 거꾸로 읽으면 본인 코드를 짤 때의 감각이 된다. 데이터가 자주 복제되며 흐르는 구간에서는 reference 타입과 명시적 잠금이, 정밀도가 누적되는 구간에서는 유리수가 default다. Swift 6의 안전성과 마찰이 생기면 `@unchecked Sendable` 같은 escape hatch를 *부끄럽지 않게* 쓰되, 어디서 안전이 깨지는지 wrapper 단위로 명확히 그어두면 된다. C API를 모던 Swift처럼 위장하려 들면 결국 둘 다 실패하지만, 둘의 책임 경계를 정확히 그으면 둘 다 잘 작동한다.
